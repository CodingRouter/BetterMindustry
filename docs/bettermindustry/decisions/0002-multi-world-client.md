# ADR-0002：多视口客户端先使用顺序场景绑定

- 状态：已接受，待原型验证
- 日期：2026-10-22

## 背景

Mindustry 客户端围绕全局 `Vars.state`、`Vars.world`、`Groups`、相机和渲染器构建。目标客户端需要同时显示多个 Sector，但立即把这些依赖全部重构为实例化上下文风险很高。

粗查当前源码：

- 345 个 Java 文件静态导入 `Vars.*`。
- 53 个文件直接使用 `Groups`。
- 约 50 个文件直接引用 `Vars.state` 或 `Vars.world`。

## 决策

M1 的多视口原型在客户端主线程顺序绑定一个 `WorldView`：

1. 网络线程只把包按 `sectorId` 放入场景队列。
2. 主线程绑定目标场景的 `state`、`world`、玩家、实体组、相机和渲染缓存。
3. 应用该场景的排队包。
4. 渲染当前视口。
5. 恢复或切换到下一个场景。

静态资源、贴图和 Shader 在视口间共享；World、GameState、实体组和渲染缓存独立。

## 约束

- 不在网络线程直接修改 Mindustry 全局状态。
- 所有扩展网络包必须携带 `sectorId`。
- 场景绑定必须使用作用域封装，退出时恢复状态。
- 多视口 MVP 不要求单进程内多线程并发 Tick。
- 服务器世界继续使用独立进程隔离。

## 长期方向

原型验证后，将全局状态逐步迁移到真正的 `GameContext`：

- `GameState`
- `World`
- Entity Groups
- Indexer 和路径服务
- 网络会话
- 每个视口的相机和渲染缓存

只有完成该迁移后，才评估同一 JVM 内承载多个世界或区块内并行模拟。
