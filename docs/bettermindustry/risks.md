# 风险清单

## 高优先级

### 全球状态与单世界假设

直接让多个地图共享一个 JVM 会牵扯静态状态、渲染、网络和存档。第一阶段以独立进程隔离，减少重写范围。

### 确定性

在线、离线和恢复模拟只要使用不同 Tick 顺序，产出就会漂移。所有加速路径必须与串行基线对拍，不能把估算结果标成精确结果。

### 上游分叉成本

大规模改动 `core` 和 `server` 会提高合并上游的成本。新平台能力尽量放在独立模块，通过小型稳定接口接触上游代码，并保存修改理由和测试。

### 协议兼容

跨世界事件和新客户端功能需要扩展协议。原版客户端不理解新能力，所以必须做版本检查与能力协商，不能默认客户端和服务端永远一致。

## 中优先级

### 多世界资源成本

每个世界一个 JVM 更安全，但 Java 堆、线程和纹理/资源会随世界数增长。需要实测空闲世界、活跃世界和离线追赶世界的内存、CPU 与磁盘占用。

### 服务端作弊面

控制 API、世界进程通道和跨世界事件都可能被滥用。管理面与玩家面分开，所有跨世界请求都要求配额、来源校验和审计。

### 视觉性能

动态光照、阴影和后期处理可能伤害低配设备体验。画质必须可分级，并以原版帧率为基线比较。

## 法律与分发

### GPL-3.0

分发修改后的客户端或服务端二进制时，需要遵守 GPL-3.0 的源代码提供和许可证要求。保留上游版权声明、许可证和来源说明；正式发布前单独审查。

### 名称与素材

“Mindustry”及其素材涉及上游权利。正式产品命名、商店页面和宣传方式需要核对上游规则；代码开源不自动等于可以冒充官方版本。
